\begin{abstract}
\texttt{dbms-go} es un motor de base de datos multimodal escrito en Go desde cero, acompañado de una interfaz web en React. En la \textbf{Parte 1} se implementaron dos organizaciones físicas de archivo (\emph{heap file} y archivo secuencial paginado), tres estructuras de indexación (B+ agrupado, B+ no agrupado y hashing extensible), un lenguaje SQL con planificador de consultas, \emph{external sorting}, \emph{external hashing} y control de concurrencia con 2PL estricto y WAL. En la \textbf{Parte 2} se agregó un índice espacial R-Tree con división estilo R*, consultas por radio, por polígono y de $k$ vecinos más cercanos ($k$-NN), expuestas por una API REST y un mapa interactivo. En la \textbf{Parte 3} se incorporó búsqueda de texto completo (\emph{Full-Text Search}) mediante construcción de índices invertidos en disco con \textbf{SPIMI} y ordenamiento por relevancia con \textbf{TF-IDF} (similitud del coseno) y \textbf{BM25}. En la \textbf{Parte 4} se extendió el motor al dominio multimedia (imágenes y audio) mediante extracción de descriptores locales (\textbf{SIFT} y \textbf{MFCC}), cuantización vectorial por \emph{k-means} (\emph{Bag of Visual/Audio Words}) e indexación aproximada de alta dimensión con \textbf{IVF-Flat} y \textbf{HNSW}. Se presentan evaluaciones experimentales sobre escalas de $1\,000$, $10\,000$ y $100\,000$ registros que cuantifican los compromisos entre latencia, precisión y costo de almacenamiento en cada subsistema.
\end{abstract}

\section{Introducción y objetivos}
% ===========================================================================

El objetivo del proyecto es construir, desde cero, las piezas internas de un sistema gestor de bases de datos multimodal y medir experimentalmente el efecto de cada decisión de diseño. En lugar de depender de motores de almacenamiento externos, el equipo implementó la organización física de los datos en disco, los índices clásicos, espaciales, textuales y vectoriales, el procesamiento de consultas SQL y una interfaz web para interactuar con ellos.

El informe cubre las siguientes partes del proyecto:

\begin{itemize}
  \item \textbf{Parte 1 -- Organización de archivos e indexación.} \emph{Heap file}, archivo secuencial paginado, B+ agrupado, B+ no agrupado, hashing extensible, lenguaje SQL, \emph{external sorting}, \emph{external hashing} y transacciones concurrentes.
  \item \textbf{Parte 2 -- Índice espacial.} R-Tree con división estilo R* y consultas por radio, por polígono y $k$-NN, integrado con una API REST y un mapa en el frontend.
  \item \textbf{Parte 3 -- Búsqueda de texto completo (\emph{Full-Text Search}).} Índice invertido construido por bloques mediante \emph{SPIMI} y métodos de ranking probabilístico y vectorial: \emph{TF-IDF con similitud del coseno} y \emph{BM25}, integrados en SQL mediante \texttt{MATCH}, \texttt{USING} y \texttt{SCORE()}.
  \item \textbf{Parte 4 -- Soporte multimedia (imágenes y audio).} Extracción de patrones locales mediante \emph{SIFT (Scale-Invariant Feature Transform)} para imágenes y \emph{MFCC (Mel-Frequency Cepstral Coefficients)} para audio, cuantización mediante \emph{k-means} para construir diccionarios de $K$ palabras visuales/acústicas e histogramas ponderados, e índices vectoriales \emph{IVF-Flat (Inverted File Index)} y \emph{HNSW (Hierarchical Navigable Small World)} bajo similitud del coseno, distancia euclidiana y producto punto.
  \item \textbf{Parte 5 -- Aplicaciones.} Integración de búsqueda multimodal en la interfaz web y aplicación de reconocimiento facial sobre el motor.
\end{itemize}

Cada parte culmina con una comparación experimental generada mediante los comandos de \emph{benchmark} del propio repositorio (Anexo~\ref{sec:reproducir}).

\section{Parte 1: organización de archivos}
% ===========================================================================

\subsection{Heap file}

El \emph{heap file} guarda las filas en el orden en que llegan, sin ningún orden por clave. Es la organización por defecto de una tabla.

\paragraph{Formato en disco.} El archivo empieza con una cabecera fija de 64 bytes, seguida de páginas de 4\,096 bytes. Cada página tiene una cabecera de 16 bytes (con espacio reservado para LSN y \emph{checksum}) y un arreglo de \emph{slots} de tamaño fijo (128 bytes por defecto):

\begin{figure}[H]
  \centering
  \begin{tikzpicture}[x=1cm,y=1cm]

    \fill[gris!30] (0,0) rectangle (1.4,0.9);

    \foreach \i/\t in {0/slot 0,1/slot 1,2/slot 2,3/slot 3} {
      \fill[suave] ({1.4+\i*2.1},0) rectangle ({3.5+\i*2.1},0.9);
      \draw[primario] ({3.5+\i*2.1},0) -- ({3.5+\i*2.1},0.9);
      \node[font=\scriptsize] at ({2.45+\i*2.1},0.45) {\t};
    }
    \node[font=\scriptsize] at (11.75,0.45) {$\cdots$ slot $m-1$};
    \node[font=\scriptsize,text=primario,align=left,anchor=west] at (1.4,-0.45) {ocupado: \texttt{[len uint32][tupla]}};
    \node[font=\scriptsize,text=acento,align=left,anchor=west] at (7.2,-0.45) {libre: \texttt{[FreeMarker][siguiente libre]}};
  \end{tikzpicture}
  \caption{Página del \emph{heap file}.}
\end{figure}

Como todos los \emph{slots} tienen el mismo tamaño, la posición de una fila depende solo de \texttt{(página, slot)}. El \textbf{RID} es, por lo tanto, estable: no cambia aunque se borren otras filas.

\paragraph{Operaciones.}
\begin{itemize}
  \item \textbf{Inserción}: se busca una página con espacio, guiándose por una pista en la cabecera del archivo (la primera página que podría tener huecos), y se usa un \emph{slot} libre de esa página; si no hay ninguna, se agrega una página nueva. Primero se escribe la página y después la cabecera, para que una falla entre ambas escrituras no pierda datos.
  \item \textbf{Eliminación}: con la estrategia \emph{FreeList}, el \emph{slot} se encadena a la lista de libres de su página y se reutiliza en la siguiente inserción. Con la estrategia alternativa \emph{MoveTheLast}, la última fila de la página se mueve al hueco para mantenerla compacta; en ese caso el RID de la fila movida cambia y se notifica a los índices.
  \item \textbf{Búsqueda}: sin índice, la única vía es recorrer el archivo completo, $O(N)$.
\end{itemize}

\subsection{Archivo secuencial paginado}

El archivo secuencial mantiene las filas \textbf{ordenadas por clave primaria}. Usa dos archivos:

\begin{itemize}
  \item \textbf{Principal} (\texttt{\_seq.dat}): filas ordenadas, en \emph{slots} de tamaño fijo \texttt{[flag][len][payload]}. El tamaño del \emph{slot} se ajusta al \emph{payload} máximo del esquema.
  \item \textbf{Auxiliar} (\texttt{\_aux.dat}): recibe las inserciones que romperían el orden del principal. En memoria se mantiene una copia ordenada de sus filas vivas.
\end{itemize}

Ambos archivos tienen una cabecera con número mágico, versión, tamaño de \emph{slot}, \emph{hash} del esquema, cantidad de \emph{slots}, cantidad de borrados y una \textbf{época}.

\paragraph{Búsqueda.} Búsqueda binaria sobre el archivo principal más búsqueda en el auxiliar ordenado: $O(\log N + \log A)$, donde $A$ es el tamaño del auxiliar.

\paragraph{Inserción.} Si la clave ya existió y su \emph{slot} en el principal está marcado como borrado, se reutiliza ese \emph{slot}, porque mantiene el orden sin reconstruir. En cualquier otro caso la fila va al auxiliar.

\paragraph{Eliminación.} Se marca el \emph{slot} con un \emph{flag} de borrado (\emph{tombstone}), que conserva su clave para no romper la búsqueda binaria.

\paragraph{Reconstrucción.} Cuando el auxiliar o los borrados superan $\max(128,\ \text{slots del principal}/10)$, se reconstruye el archivo: se fusionan en orden las filas vivas del principal y del auxiliar, se escribe un principal nuevo y se vacía el auxiliar. La época se incrementa en cada reconstrucción. Si el sistema se cae a mitad de camino, al abrir se descarta el auxiliar de una época anterior y el temporal incompleto.

\section{Parte 1: estructuras de indexación}
% ===========================================================================

Los tres índices viven en memoria y se reconstruyen desde el archivo de datos al abrir la tabla. Las claves se codifican en bytes con un codificador común (\texttt{storage.EncodeKey}), por lo que sirven enteros, booleanos, cadenas y claves compuestas.

\subsection{B+ no agrupado}

Es un índice secundario: asocia \emph{clave} $\to$ \emph{RID} en el \emph{heap file}. Es el índice por defecto de una tabla no agrupada.

\begin{itemize}
  \item Los nodos internos guardan claves separadoras; las hojas guardan, por clave, un \emph{bucket} con todos los RIDs de esa clave. Así una clave duplicada nunca se reparte entre dos hojas.
  \item Las hojas forman una \textbf{lista enlazada}, lo que permite resolver rangos bajando una sola vez y avanzando por las hojas.
  \item Búsqueda, inserción y rango son $O(\log_b N)$, con $b$ el orden del árbol (50 por defecto).
  \item Leer cada fila del rango requiere un acceso aleatorio al \emph{heap}, porque el orden del índice no coincide con el orden físico.
\end{itemize}

\subsection{B+ agrupado}

En una tabla agrupada (\texttt{CREATE TABLE \dots\ CLUSTERED BY (pk)}), los datos viven en el archivo secuencial ordenados por la clave primaria, y el B+ agrupado indexa esa clave. El orden del índice coincide con el orden físico, por lo que el recorrido completo en orden de clave es una lectura secuencial. Los índices secundarios de una tabla agrupada apuntan a la clave primaria en lugar de a un RID.

\paragraph{Eliminación.} Por simplicidad, la eliminación en el B+ reconstruye el árbol a partir de las entradas restantes, por lo que cuesta $O(N)$. Inserción, búsqueda y rango mantienen el costo logarítmico. Esta decisión se refleja en los experimentos de altas y bajas (Sección~\ref{sec:exp-indices}).

\subsection{Hashing extensible}

Es un índice dinámico de igualdad: un \textbf{directorio} de $2^{d}$ punteros (profundidad global $d$) a \textbf{cubetas} con profundidad local $d' \le d$.

\begin{itemize}
  \item \textbf{Inserción}: si la cubeta se llena, se divide en dos ($d'{+}{+}$) y se redistribuyen sus claves. Solo cuando $d' = d$ se duplica el directorio.
  \item \textbf{Eliminación}: las cubetas ``hermanas'' que quedan casi vacías se fusionan, y el directorio se reduce cuando ya no hace falta su profundidad, de modo que el índice también encoge.
  \item La profundidad máxima es 24 ($2^{24}$ punteros). Una cubeta puede exceder su capacidad solo si muchas filas comparten la misma clave o todos los bits del \emph{hash}.
  \item Búsqueda $O(1)$ esperado. \textbf{No soporta rangos ni orden}: esas consultas obligan a recorrer el \emph{heap}.
\end{itemize}

\section{Parte 1: procesamiento de consultas}
% ===========================================================================

\subsection{Lenguaje SQL}

El motor incluye un lexer y un parser propios. El subconjunto soportado incluye:

\begin{lstlisting}[style=sql]
CREATE TABLE alumno (id INT PRIMARY KEY, nombre VARCHAR(64), edad INT);
CREATE TABLE curso CLUSTERED BY (id) (id INT PRIMARY KEY, nombre VARCHAR(64));
CREATE INDEX hash_nombre ON alumno (nombre);   -- hashing extensible
CREATE INDEX idx_edad    ON alumno (edad);     -- B+ no agrupado
INSERT INTO alumno (id, nombre, edad) VALUES (1, 'Ana', 20);
SELECT nombre, COUNT(*) FROM alumno WHERE edad > 18
  GROUP BY nombre HAVING COUNT(*) > 1 ORDER BY nombre DESC LIMIT 10;
UPDATE alumno SET edad = 21 WHERE id = 1;
DELETE FROM alumno WHERE id = 1;
SELECT a.nombre, m.curso FROM alumno a
  JOIN matricula m ON a.id = m.alumno_id;     -- también LEFT, CROSS y USING
BEGIN TRANSACTION;                            -- END TRANSACTION / COMMIT / ROLLBACK
\end{lstlisting}

Las consultas espaciales (\texttt{POINT}, \texttt{distancia}, \texttt{dentro}) se describen en la Sección~\ref{sec:sql-espacial}, las de texto completo (\texttt{MATCH}, \texttt{USING}, \texttt{SCORE}) en la Sección~\ref{sec:sql-texto}, y las consultas vectoriales y multimedia (\texttt{VECTOR}, \texttt{AUDIO\_VECTOR}, \texttt{IMAGE\_VECTOR}, \texttt{vector\_distance}) en la Sección~\ref{sec:sql-multimedia}.

El tipo de índice se elige con una convención de nombres: el índice de la clave primaria de una tabla agrupada es el B+ agrupado; los nombres que empiezan con \texttt{hash} crean un hashing extensible, y cualquier otro nombre crea un B+ no agrupado.

\subsection{Planificador}

El planificador descompone el \texttt{WHERE} en condiciones unidas por \texttt{AND} y busca un índice que las resuelva:

\begin{itemize}
  \item Igualdad sobre una columna indexada: \emph{index seek} en el hash o en el B+.
  \item Desigualdades o rangos: \emph{index scan} sobre un B+. El hash nunca se usa para rangos.
  \item Condiciones espaciales sobre una columna \texttt{POINT}: búsqueda por radio, $k$-NN o polígono en el R-Tree (Sección~\ref{sec:sql-espacial}).
  \item Condiciones de texto completo (\texttt{MATCH}): recorrido del índice invertido SPIMI con ranking TF-IDF o BM25 (Sección~\ref{sec:sql-texto}).
  \item Sin índice aplicable: recorrido secuencial del archivo.
  \item Consultas $k$-NN vectoriales y multimedia (\texttt{ORDER BY vector\_distance(...) LIMIT k}): búsqueda aproximada sobre índices \texttt{IVF}, \texttt{HNSW}, \texttt{AUDIO} o \texttt{IMAGE} (Sección~\ref{sec:sql-multimedia}).
\end{itemize}

Cuando el índice resuelve solo una parte del \texttt{WHERE}, el resto de la condición se aplica como filtro residual sobre las filas que devolvió el índice.

Cada consulta devuelve su \textbf{plan de ejecución} como una lista de pasos (\emph{seq-scan}, \emph{index-seek}, \emph{group-by}, \emph{sort}, \emph{project}, \dots) con el número de filas de cada uno, que el frontend muestra al usuario.

\subsection{External sorting}

\texttt{ORDER BY} usa un \emph{external sort} clásico: las filas se acumulan en un \emph{buffer} de tamaño fijo; cuando se llena, se ordena y se vuelca como un \emph{run}. Al final, si hubo más de un \emph{run}, se hace un \emph{k-way merge} con una cola de prioridad. Existe un modo que escribe los \emph{runs} en archivos temporales, lo que acota la memoria al tamaño del \emph{buffer}.

\subsection{JOIN y GROUP BY con \emph{external hashing}}

El paquete \texttt{external/hashing} reparte un conjunto de filas en $P$ particiones según el hash (FNV-1a) de una clave, de forma que todas las filas con la misma clave caen en la misma partición. Si las filas no caben en el \emph{buffer}, cada partición se escribe en un archivo temporal y se vuelve a leer cuando le toca; así, la tabla hash en memoria solo tiene que contener una partición a la vez. $P$ se elige para que cada partición quepa en el \emph{buffer}.

\textbf{GROUP BY.} Las filas se particionan por el valor de las expresiones de agrupación y cada partición se agrupa con una tabla hash. Los grupos se devuelven en el orden en que aparece su primera fila.

\textbf{JOIN.} El resultado de un \emph{join} es una tabla virtual cuyas columnas se califican como \texttt{alias.columna}; el resto del \emph{pipeline} del \texttt{SELECT} (\texttt{WHERE}, \texttt{GROUP BY}, \texttt{ORDER BY}, \texttt{LIMIT}) trabaja sobre ella como si fuera una tabla. Para cada \texttt{JOIN} el planificador elige una estrategia:

\begin{itemize}
  \item \textbf{Index nested loop}: si la tabla de la derecha tiene un índice (B+ o hash) sobre su columna de unión, por cada fila de la izquierda se hace una búsqueda exacta en el índice.
  \item \textbf{Grace hash join}: si no hay índice, los dos lados se particionan con el mismo $P$ y la misma función de hash, y cada par de particiones se une con una tabla hash construida sobre la derecha (\emph{build}) y recorrida con la izquierda (\emph{probe}).
  \item \textbf{Nested loop}: para \texttt{CROSS JOIN} o condiciones que no son igualdades entre columnas.
\end{itemize}

Las condiciones del \texttt{WHERE} que solo usan columnas de la primera tabla se empujan a su acceso (\emph{predicate pushdown}), para que el planificador pueda usar sus índices antes del \emph{join}. Se soportan \texttt{INNER}, \texttt{LEFT}, \texttt{CROSS} y \texttt{USING}; \texttt{LEFT JOIN} completa con \texttt{NULL} las filas sin pareja.

\section{Parte 1: transacciones y concurrencia}
\label{sec:concurrencia}
% ===========================================================================

\subsection{Transacciones y recuperación}

\texttt{BEGIN TRANSACTION} abre una transacción y \texttt{END TRANSACTION} (o \texttt{COMMIT}) la confirma; \texttt{ROLLBACK} la deshace, también hasta un \texttt{SAVEPOINT}. Cada cambio se escribe primero en un \emph{write-ahead log} (WAL) con su valor anterior y después se aplica a los archivos. El \texttt{COMMIT} fuerza su registro a disco; el \texttt{ROLLBACK} recorre los cambios en orden inverso y los revierte. Si el proceso se corta, el siguiente arranque deshace con el WAL todo lo que no tenga \texttt{COMMIT}.

\subsection{Sesiones y bloqueo en dos fases estricto}

Cada usuario (o hilo) trabaja con su propia \textbf{sesión}, que tiene como mucho una transacción abierta; varias sesiones ejecutan sentencias a la vez. El aislamiento se obtiene con \textbf{bloqueo en dos fases estricto} (2PL estricto):

\begin{enumerate}
  \item Antes de ejecutar una sentencia, la sesión bloquea cada tabla que toca: compartido (S) para leer y exclusivo (X) para escribir o para DDL. Si otra transacción tiene un bloqueo incompatible, la sesión espera sin detener al resto del motor.
  \item Dentro de una transacción los bloqueos se conservan hasta el \texttt{COMMIT} o el \texttt{ROLLBACK}, así que nadie lee cambios sin confirmar (no hay lecturas sucias) ni los sobrescribe. Fuera de una transacción se liberan al terminar la sentencia.
  \item Con los bloqueos concedidos, la sentencia se ejecuta de forma atómica frente a las de otras sesiones.
\end{enumerate}

Además de los bloqueos de tabla, la transacción bloquea la clave primaria de cada fila que lee (S) o modifica (X). El plan de ejecución muestra qué bloqueos tomó cada sentencia y cuánto esperó.

\subsection{Detección de deadlocks}

El gestor de bloqueos mantiene un \textbf{grafo de espera}: una arista $T_1 \rightarrow T_2$ indica que $T_1$ espera un bloqueo que tiene $T_2$, o que $T_2$ pidió antes en la misma cola. Cuando una petición tendría que esperar, se comprueba si cerraría un ciclo; en ese caso la transacción que pidió el bloqueo es la \textbf{víctima}: la petición se rechaza, la transacción se deshace entera (\texttt{ROLLBACK} automático) y sus bloqueos se liberan para que las demás avancen. El cliente recibe un error de \emph{deadlock} y puede reintentar.

Implementar la eliminación con redistribución y fusión de nodos es la mejora más importante pendiente.

\subsection{Estructura}

El R-Tree indexa puntos \texttt{(latitud, longitud)}. Cada hoja guarda puntos junto con el RID de su fila, y cada nodo interno guarda hijos. \paragraph{Inserción.} Se desciende por el hijo cuyo MBR necesita \textbf{crecer menos} para incluir el punto; si hay empate, el de menor área. Si la hoja se desborda, se divide y la división se propaga hacia arriba.

\subsection{División estilo R*-tree}

La primera versión dividía siempre por longitud a la mitad. Eso producía rectángulos largos y muy solapados en latitud, y el árbol casi no podía descartar ramas. La versión final usa una variante simplificada de la división del R*-tree~\cite{beckmann1990}:

\begin{enumerate}
  \item Para cada eje (latitud y longitud) se ordenan los elementos y se prueban todos los cortes válidos. Se elige el eje con \textbf{menor suma de márgenes} (semiperímetros), es decir, el que produce rectángulos más ``cuadrados''.
  \item En ese eje se elige el corte con \textbf{menor solapamiento} entre los dos grupos; si empatan, el de menor área total, y luego el más cercano al centro.
  \item Cada grupo conserva al menos $\approx$40\% de las entradas del nodo.
\end{enumerate}

Con puntos alineados el área de los rectángulos es 0, por lo que el margen sirve también como desempate.

\subsection{Métricas de distancia}

Se soportan dos métricas:
\begin{align*}
  d_{\text{euclídea}} &= \sqrt{\Delta\text{lat}^2 + \Delta\text{lon}^2} \quad\text{(en grados)}\\[2pt]
  h &= \sin^2\!\tfrac{\Delta\varphi}{2} + \cos\varphi_1\cos\varphi_2\sin^2\!\tfrac{\Delta\lambda}{2},
  \qquad d_{\text{Haversine}} = 2R\,\operatorname{atan2}\!\big(\sqrt{h},\sqrt{1-h}\big)
\end{align*}
con $R = 6\,371$~km. Haversine da la distancia real sobre la superficie terrestre, en kilómetros.

\subsection{Consultas}

\paragraph{Por radio.} Se proyecta el círculo de radio $r$ a un rectángulo en grados, que sirve de prefiltro: se descartan las ramas cuyo MBR no lo intersecta. Sobre los candidatos, la distancia exacta decide qué puntos entran.

\paragraph{$k$ vecinos más cercanos.} Se usa la búsqueda \emph{best-first} de Hjaltason y Samet~\cite{hjaltason1999}. Una cola de prioridad mezcla nodos y puntos:
\begin{itemize}
  \item la prioridad de un nodo es $\text{MINDIST}(q, \text{MBR})$, una cota inferior de la distancia de $q$ a cualquier punto del rectángulo;
  \item la prioridad de un punto es su distancia exacta a $q$.
\end{itemize}
Siempre se extrae lo más cercano. Si es un nodo, se encolan sus hijos; si es un punto, ese es el siguiente vecino, porque todo lo que queda en la cola tiene una cota inferior mayor o igual. El algoritmo termina al tener $k$ puntos y solo visita las ramas que pueden contener alguno de ellos.

Para que el resultado sea correcto, MINDIST debe ser una cota inferior real en la misma métrica. Con Haversine, si $q$ cae dentro del rectángulo la cota es 0; si no, se calcula la distancia geodésica mínima a sus bordes. Para los bordes que son meridianos, se calcula el pie de la perpendicular $\varphi^* = \arctan(B/A)$ y, si cae fuera del segmento, se usa el extremo más cercano. Esta versión no contempla rectángulos que crucen el antimeridiano ($\pm180^\circ$).

\paragraph{Por polígono.} Devuelve los puntos dentro de un polígono arbitrario, que puede ser cóncavo y tener cualquier orientación. La pertenencia de un punto se decide con la regla \textbf{par-impar}, y los puntos sobre el borde cuentan como dentro. Para podar el árbol, cada MBR se clasifica respecto del polígono:
\begin{itemize}
  \item \textbf{fuera}: se descarta toda la rama;
  \item \textbf{dentro}: se devuelve todo lo que hay debajo, sin probar punto por punto;
  \item \textbf{parcial}: se desciende y se prueba cada punto.
\end{itemize}
Un margen de $\approx$0.1~mm hace que lo muy cercano a una arista se decida siempre punto por punto, lo que evita errores de redondeo. El polígono se valida antes de buscar: al menos 3 vértices y coordenadas finitas.

\subsection{Extensión SQL espacial}
\label{sec:sql-espacial}

El motor tiene un tipo de columna \texttt{POINT}. Un punto se guarda como texto canónico \texttt{POINT(lat lon)} (el almacenamiento no tiene tipo flotante) y toda columna \texttt{POINT} lleva un índice R-Tree, \texttt{rtree\_<columna>}, que se mantiene en cada \texttt{INSERT}, \texttt{UPDATE} y \texttt{DELETE} y se reconstruye al abrir la base. Las funciones disponibles son:

\begin{itemize}
  \item \texttt{POINT(lat, lon)} y \texttt{POLYGON(p1, p2, \dots)} construyen valores.
  \item \texttt{distancia(a, b)} devuelve la distancia geodésica (Haversine) en metros; \texttt{distancia(a, b, 'euclidean')} devuelve la distancia euclidiana en grados.
  \item \texttt{dentro(p, polígono)} indica si el punto cae dentro del polígono.
\end{itemize}

\begin{lstlisting}[style=sql]
CREATE TABLE tiendas (id INT PRIMARY KEY, nombre VARCHAR(40), ubicacion POINT);
INSERT INTO tiendas VALUES (1, 'Centro', POINT(-12.0464, -77.0428));
-- rango: tiendas a menos de 5 km
SELECT * FROM tiendas WHERE distancia(ubicacion, POINT(-12.0464, -77.0428)) < 5000;
-- k-NN: las 10 más cercanas
SELECT * FROM tiendas ORDER BY distancia(ubicacion, POINT(-12.0464, -77.0428)) LIMIT 10;
-- intersección con un polígono (por ejemplo, un distrito)
SELECT * FROM tiendas WHERE dentro(ubicacion,
  POLYGON(POINT(-12.04,-77.05), POINT(-12.04,-77.03), POINT(-12.06,-77.03))) = true;
\end{lstlisting}

El planificador reconoce estos patrones y los resuelve con el R-Tree: \texttt{distancia(col, punto) < r} se convierte en una búsqueda por radio, \texttt{dentro(col, polígono)} en la búsqueda por polígono, y \texttt{ORDER BY distancia(col, punto) LIMIT k} en el $k$-NN \emph{best-first}, sin ordenar la tabla. Con otras condiciones en el \texttt{WHERE}, el resto se aplica como filtro residual; si el patrón no se puede resolver con el índice (por ejemplo, $k$-NN con un \texttt{WHERE} adicional), la consulta se ejecuta con recorrido secuencial y \emph{external sort}, con el mismo resultado.

\subsection{Metodología}

Se comparan tres técnicas sobre los mismos datos:
\begin{itemize}
  \item \textbf{Secuencial}: recorrido completo sin índice; para $k$-NN se recorre todo conservando los $k$ mejores.
  \item \textbf{R-Tree} del proyecto, con 16 entradas máximas por nodo.
  \item \textbf{GiST de PostgreSQL}, sin PostGIS. Para el radio se indexa una columna \texttt{box} (operador \texttt{\&\&}) y encima se calcula Haversine exacto, la misma estrategia que el R-Tree. Para $k$-NN se usa el operador nativo \texttt{ORDER BY pt <-> centro LIMIT k}. Se construyen ambos índices y se reporta la suma.
\end{itemize}

Los puntos se generan uniformemente en una caja de Lima (latitud $-12.10$ a $-11.90$, longitud $-77.20$ a $-76.90$) con semilla fija. Se lanzan 100 consultas por medición, con centros generados con otra semilla, y se reporta el promedio. Las consultas por radio usan Haversine con radios de 1, 5 y 10~km. Las de $k$-NN usan distancia euclídea en grados, que es la nativa del operador \texttt{<->} de GiST, con $k \in \{10, 50, 100\}$. Las tres técnicas devuelven el mismo número de filas, lo que se verifica en cada medición.

\paragraph{Consideraciones.} El R-Tree vive en memoria y se mide dentro del mismo proceso; su espacio es memoria. GiST se mide con \texttt{\textbackslash timing} de \texttt{psql}, que incluye el análisis y la planificación de la consulta y la comunicación con el servidor, y su espacio es disco. La comparación es útil para ubicar el orden de magnitud, pero favorece al R-Tree.

\subsection{Análisis}

\begin{itemize}
  \item \textbf{$k$-NN.} Es donde el índice rinde más. Con 100\,000 puntos y $k=10$, el R-Tree responde en 0.023~ms: unas \textbf{580 veces más rápido} que el recorrido secuencial (13.4~ms) y unas \textbf{8 veces} más rápido que GiST (0.18~ms). Al multiplicar los datos por 100, el tiempo del R-Tree solo se duplica, mientras que el secuencial crece unas 90 veces. GiST también se mantiene casi constante, pero con un costo fijo por consulta de $\approx$0.13--0.28~ms.
  \item \textbf{Radio.} El R-Tree es el más rápido en todos los casos, pero la ventaja depende de la \textbf{selectividad}. Con radio de 1~km (0.4\% de los puntos) es 117 veces más rápido que el secuencial; con 10~km (30\% de los puntos), solo 2.3 veces, porque igual tiene que visitar y devolver casi un tercio del conjunto. En ese caso GiST (18.2~ms) es incluso más lento que el secuencial (11.7~ms), por el costo de producir y transferir $\approx$30\,000 filas.
  \item \textbf{Construcción y espacio.} El R-Tree se construye unas 3.4 veces más rápido que los dos índices GiST y ocupa unas 2.6 veces menos ($\approx$54 bytes por punto frente a $\approx$142). Parte de la diferencia viene de que GiST guarda páginas en disco con su propia cabecera y relleno, y mantiene dos índices.
  \item \textbf{Conclusión.} Un índice espacial vale la pena sobre todo para consultas selectivas y para $k$-NN, donde evita recorrer todo el conjunto. Para consultas que devuelven una fracción grande de los datos, el beneficio se reduce mucho.
\end{itemize}

\section{Parte 3: búsqueda de texto completo (\emph{Full-Text Search})}
% ===========================================================================

La búsqueda de texto completo (\emph{Full-Text Search}) permite recuperar documentos por su contenido y ordenarlos según su relevancia. A diferencia de una comparación literal con \texttt{LIKE}, considera la frecuencia e importancia discriminativa de los términos buscados. El objetivo de esta parte es construir un índice invertido escalable en disco mediante \textbf{SPIMI} y evaluar dos esquemas de ranking: \textbf{TF-IDF con similitud del coseno} y \textbf{BM25}.

\subsection{Flujo de procesamiento}

El procesamiento de texto sigue un flujo en cuatro etapas:
\begin{center}
\fbox{Documentos} $\longrightarrow$ \fbox{Preprocesamiento} $\longrightarrow$ \fbox{Índice SPIMI}
$\longrightarrow$ \fbox{Ranking TF-IDF / BM25} $\longrightarrow$ \fbox{Resultados SQL}
\end{center}

SPIMI organiza los términos en listas de publicaciones para localizar documentos candidatos sin recorrer la colección completa. Posteriormente, TF-IDF o BM25 asigna una puntuación numérica que permite ordenar los resultados por relevancia.

\subsection{Preprocesamiento e índice invertido}

Antes de indexar un texto se aplica: conversión a minúsculas, normalización de acentos, eliminación de signos de puntuación, tokenización, filtrado de palabras vacías (\emph{stop words}) y reducción a raíces (\emph{stemming}) con Snowball . Se emplea exactamente el mismo preprocesamiento tanto para los documentos indexados como para las consultas.

Un \textbf{índice invertido} relaciona cada término del vocabulario con la lista de documentos donde aparece:
\begin{table}[H]
  \centering
  \small
  \begin{tabular}{@{}ll@{}}
    \toprule
    \textbf{Término} & \textbf{Lista de publicaciones (\emph{postings})} \\
    \midrule
    \texttt{base} & $(D_0,2), (D_1,1)$ \\
    \texttt{vectorial} & $(D_1,1)$ \\
    \texttt{datos} & $(D_0,1), (D_1,1)$ \\
    \bottomrule
  \end{tabular}
  \caption{Ejemplo de estructura de listas de publicaciones en el índice invertido.}
\end{table}

Cada par $(D_i, tf)$ indica el identificador del documento y la frecuencia de aparición del término dentro de él.

\subsection{Construcción del índice con SPIMI y gestión de memoria}

\textbf{SPIMI} (\emph{Single-Pass In-Memory Indexing})~\cite{manning2008} construye el índice por bloques en una sola pasada. En lugar de mantener todas las publicaciones de la colección en RAM, acumula entradas en un diccionario en memoria hasta alcanzar un umbral y vuelca cada bloque ordenado a disco.

\begin{lstlisting}[style=pseudo,caption={Pseudocódigo simplificado de construcción con SPIMI}]
para cada documento:
    tokens = preprocesar(documento)
    contar frecuencia de cada termino
    agregar (DocID, frecuencia) al diccionario
    si publicaciones_pendientes >= limite:
        escribir bloque ordenado en disco
        liberar diccionario de RAM
al finalizar:
    escribir ultimo bloque
    mezclar bloques y publicar indice
\end{lstlisting}

\paragraph{Administración de memoria RAM.} La construcción controla el consumo mediante un \textbf{límite de publicaciones pendientes}, no un límite rígido en bytes. En \texttt{builder.go}, el umbral predeterminado es:
\[
\texttt{MaxBlockPostings} = 2^{19} = 524\,288.
\]
Cada publicación corresponde a un par término--documento; las repeticiones de una palabra dentro de un mismo documento se acumulan en su frecuencia $tf$. El volcado a disco se ejecuta al finalizar el documento que alcanza o supera el umbral, por lo que el límite puede excederse ligeramente sin fragmentar documentos.

\subsection{Proceso Merge y uso del Min-Heap}

Cuando un término aparece en múltiples bloques intermedios, sus listas de publicaciones deben fusionarse en orden. Para ello, la implementación abre lectores secuenciales por bloque y emplea un \textbf{Min-Heap} ordenado lexicográficamente por término:

\begin{table}[H]
  \centering
  \small
  \begin{tabular}{@{}ll@{}}
    \toprule
    \textbf{Bloque} & \textbf{Contenido} \\
    \midrule
    Bloque 1 & \texttt{base} $\to (D_0,1)$; \texttt{datos} $\to (D_0,2)$ \\
    Bloque 2 & \texttt{base} $\to (D_1,2)$; \texttt{indice} $\to (D_1,1)$ \\
    \midrule
    Resultado combinado & \texttt{base} $\to (D_0,1), (D_1,2)$ \\
    \bottomrule
  \end{tabular}
  \caption{Fusión externa de listas de publicaciones entre bloques SPIMI.}
\end{table}

El algoritmo extrae repetidamente el término mínimo del \emph{heap}, reúne todas sus listas desde los lectores que comparten ese término, escribe la entrada consolidada en el archivo final y avanza únicamente los cursores involucrados. De este modo, \textbf{el Merge nunca carga los bloques completos en RAM}. Si el número de bloques supera el factor máximo de apertura simultánea (\texttt{MaxFanIn} $= 64$), la función \texttt{reduceBlocks()} ejecuta rondas jerárquicas de fusión.

\subsection{Ranking TF-IDF y similitud del coseno}

\textbf{TF-IDF} pondera cada término según su frecuencia local en el documento y su rareza global en la colección:
\begin{align*}
  \mathrm{TF}(t,d) &= 1 + \ln(tf_{t,d}), \\
  \mathrm{IDF}(t)  &= \ln\!\left(\frac{N}{df_t}\right), \\
  w_{t,d}          &= \mathrm{TF}(t,d)\,\mathrm{IDF}(t),
\end{align*}
donde $tf_{t,d}$ es la frecuencia del término $t$ en el documento $d$, $df_t$ es el número de documentos que contienen a $t$ y $N$ el total de documentos. Documentos y consulta se modelan como vectores dispersos y se comparan mediante la \textbf{similitud del coseno}:
\[
\operatorname{sim}(d,q) = \frac{\vec{d}\cdot\vec{q}}{\|\vec{d}\|\,\|\vec{q}\|}.
\]
Las normas euclidianas $\|\vec{d}\|$ se precalculan al construir el índice y, durante la consulta, se recorren únicamente las listas de \emph{postings} de los términos presentes en $q$, manteniendo los $k$ mejores resultados en un \emph{Min-Heap}.

\subsection{Ranking BM25}

\textbf{BM25}~\cite{robertson2009} es un modelo probabilístico de recuperación de información que incorpora saturación no lineal de frecuencia de término y normalización explícita respecto a la longitud del documento:
\[
\operatorname{BM25}(d,q) = \sum_{t \in q} \ln\!\left(1 + \frac{N - df_t + 0.5}{df_t + 0.5}\right)
\frac{tf_{t,d}(k_1 + 1)}{tf_{t,d} + k_1\left(1 - b + b\frac{|d|}{\mathrm{avgdl}}\right)},
\]
donde $|d|$ es la longitud en tokens del documento $d$ y $\mathrm{avgdl}$ la longitud promedio de la colección. El parámetro $k_1$ regula la saturación por repetición de términos y $b$ controla la penalización por longitud del documento; en el motor se fijan por defecto en $k_1 = 1.2$ y $b = 0.75$.

  \centering
  \small
  \begin{tabular}{@{}p{3.2cm}p{5.2cm}p{5.2cm}@{}}
    \toprule
    \textbf{Criterio} & \textbf{TF-IDF + coseno} & \textbf{BM25} \\
    \midrule
    Enfoque & Espacio vectorial ponderado & Modelo probabilístico de relevancia \\
    Frecuencia ($tf$) & Crecimiento logarítmico ($1 + \ln tf$) & Saturación asintótica controlada por $k_1$ \\
    Longitud del doc. & Normalización L2 implícita del vector & Normalización explícita mediante $|d|/\mathrm{avgdl}$ y $b$ \\
    Escala de salida & Acotada en $[0, 1]$ & No acotada (se compara orden relativo) \\
    \bottomrule
  \end{tabular}

\subsection{Extensión SQL e integración con el motor}
\label{sec:sql-texto}

El parser y el planificador incorporan el predicado \texttt{MATCH(columna, 'consulta')}, la cláusula \texttt{USING TF\_IDF | BM25} y la función escalar \texttt{SCORE()}:

\begin{lstlisting}[style=sql,caption={Consultas de búsqueda de texto completo con TF-IDF y BM25}]
SELECT *, SCORE() AS relevancia
FROM documentos
WHERE MATCH(contenido, 'base de datos vectorial')
USING TF_IDF
ORDER BY relevancia DESC
LIMIT 10;

SELECT *, SCORE() AS relevancia
FROM articulos
WHERE MATCH(texto, 'machine learning')
USING BM25
ORDER BY relevancia DESC;
\end{lstlisting}

Al ejecutar por primera vez una búsqueda textual sobre una columna, el motor construye el índice SPIMI en disco y lo reutiliza en consultas posteriores. Ante operaciones de modificación (\texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}), el índice textual se invalida para garantizar consistencia. El plan de ejecución reporta un nodo \texttt{IndexScan} sobre SPIMI junto con el algoritmo de ranking seleccionado.

\section{Parte 4: soporte multimedia (imágenes y audio)}
\label{sec:parte4}
% ===========================================================================

Los índices clásicos (árboles B+ y hashing) y espaciales (R-Tree) pierden eficiencia cuando los objetos se representan mediante vectores densos o dispersos de decenas o cientos de dimensiones debido a la \emph{maldición de la dimensionalidad}. Para soportar consultas por similitud de contenido sobre imágenes y pistas de audio, el motor incorpora una tubería en dos etapas: (1) transformación de los archivos multimedia en vectores numéricos normalizados mediante extracción de descriptores locales y cuantización vectorial, y (2) indexación aproximada de vecinos más cercanos (\emph{Approximate Nearest Neighbors}, ANN) con \textbf{IVF-Flat} y \textbf{HNSW}.

\subsection{Extracción de descriptores locales: SIFT y MFCC}

En lugar de comparar archivos binarios completos, el motor extrae firmas acústicas o visuales compactas (\texttt{dbms/lib/local\_features/}):

\begin{itemize}
  \item \textbf{Imágenes -- SIFT (\emph{Scale-Invariant Feature Transform})~\cite{lowe2004}:} detecta puntos clave extremos en el espacio de escalas mediante diferencias de gaussianas (DoG), asigna una orientación dominante a cada punto y construye histogramas locales de gradientes de $128$ dimensiones invariantes a traslación, escala y rotación (\texttt{local\_features/sift}).
  \item \textbf{Audio -- MFCC (\emph{Mel-Frequency Cepstral Coefficients})~\cite{davis1980}:} segmenta la señal de audio PCM en tramas cortas solapadas con ventana de Hamming, calcula el espectro de potencia mediante Transformada Rápida de Fourier (FFT), proyecta las energías sobre un banco de filtros triangulares espaciados en la escala perceptual Mel, aplica compresión logarítmica y extrae los coeficientes cepstrales mediante Transformada Discreta del Coseno (DCT) (\texttt{local\_features/mfcc}).
\end{itemize}

\subsection{Cuantización vectorial y representación BoVW / BoAW}

Dado que cada imagen o pista de audio produce un número variable de descriptores locales, estos se proyectan a un espacio vectorial de dimensión fija $K$ mediante el modelo de \emph{Bolsa de Palabras Visuales/Acústicas} (\emph{Bag of Visual/Audio Words}, BoVW / BoAW)~\cite{jegou2011}:

\begin{enumerate}
  \item \textbf{Construcción del vocabulario:} sobre una muestra de descriptores locales de la colección se ejecuta agrupamiento \emph{k-means} para obtener $K$ centroides representativos ($\mathcal{C} = \{c_1, \dots, c_K\}$). El vocabulario resultante se serializa en disco (\texttt{vocab.gob}) para reutilizarlo en inserciones y consultas posteriores.
  \item \textbf{Codificación y ponderación TF-IDF:} cada descriptor local $x_j$ de un objeto se asigna a su centroide más cercano $c_i = \arg\min_{c \in \mathcal{C}} \|x_j - c\|_2$, generando un histograma de frecuencias $tf_i$. Para atenuar el peso de patrones acústicos o visuales omnipresentes, cada componente se pondera con su frecuencia inversa de documento y se normaliza bajo norma euclidiana L2:
  \[
    v_i = tf_i \cdot \ln\!\left(\frac{N}{df_i}\right), \qquad \hat{v} = \frac{\vec{v}}{\|\vec{v}\|_2}.
  \]
\end{enumerate}

En el módulo de audio (\texttt{dbms/lib/vector/audio\_features.go}), este proceso produce vectores normalizados de $K = 128$ dimensiones por pista.

\subsection{Índices vectoriales de alta dimensión: IVF-Flat y HNSW}

Para acelerar las consultas de $k$ vecinos más cercanos ($k$-NN) bajo \textbf{Similitud del Coseno}, \textbf{Distancia Euclidiana} y \textbf{Producto Punto}, se implementaron dos estructuras de indexación (\texttt{dbms/lib/index/}):

\paragraph{IVF-Flat (\emph{Inverted File Index}).}
Particiona el espacio vectorial en $\text{nlist}$ celdas de Voronoi mediante entrenamiento \emph{k-means++} determinista (\texttt{ivf/ivfflat.go}). Cuando la métrica es \texttt{Cosine}, el algoritmo aplica \emph{k-means} esférico (normalizando tanto vectores como centroides en cada iteración); para \texttt{Euclidean}, utiliza \emph{k-means} clásico. Cada vector insertado se almacena sin compresión en la lista invertida (\texttt{invertedList}) de su centroide más cercano, manteniendo un mapa de posiciones (\texttt{positions}) para soportar actualizaciones y borrados. Durante una consulta, se calculan las distancias a los $\text{nlist}$ centroides y se exploran únicamente las $\text{nprobe}$ listas más próximas ($\text{nprobe} \le \text{nlist}$), reduciendo el espacio de búsqueda a una fracción $\approx \text{nprobe}/\text{nlist}$ del total.

\paragraph{HNSW (\emph{Hierarchical Navigable Small World})~\cite{malkov2020}.}
Construye un grafo de proximidad multicapa (\texttt{hnsw/hnsw.go}) donde los niveles superiores contienen enlaces de largo alcance que permiten saltar rápidamente hacia la vecindad de la consulta, mientras que la capa base (nivel 0) concentra conexiones densas de corto alcance. Su construcción y búsqueda se gobiernan por el grado máximo por nodo $M$, el ancho de haz durante la inserción (\texttt{efConstruction}) y el ancho de exploración en consulta (\texttt{efSearch}).

\subsection{Extensión SQL multimedia e integración con el sistema}
\label{sec:sql-multimedia}

El motor extiende el lenguaje SQL con el tipo de dato vectorial \texttt{VECTOR(D)}, cuatro variantes de índices aproximados (\texttt{IVF}, \texttt{HNSW}, \texttt{AUDIO} e \texttt{IMAGE}) y funciones escalares de extracción y distancia (\texttt{dbms/lib/sql/vector.go}, \texttt{hnsw.go}, \texttt{audio.go}, \texttt{image.go}):

\begin{itemize}
  \item \textbf{Índices sobre vectores explícitos (\texttt{VECTOR(D)}):} mediante \texttt{USING IVF} y \texttt{USING HNSW} con parámetros configurables en la cláusula \texttt{WITH} (\texttt{nlist}, \texttt{nprobe}, \texttt{M}, \texttt{ef\_construction}, \texttt{ef\_search} y \texttt{metric} $\in \{\text{\texttt{'cosine'}}, \text{\texttt{'euclidean'}}, \text{\texttt{'dot'}}\}$).
  \item \textbf{Índices multimedia (\texttt{USING AUDIO} y \texttt{USING IMAGE}):} operan directamente sobre columnas de texto (\texttt{VARCHAR}) que almacenan la ruta del archivo multimedia. Al crearse el índice, el motor extrae los descriptores locales de toda la tabla (MFCC o SIFT), entrena y persiste el vocabulario de $k$ palabras acústicas o visuales (\emph{codebook}) y construye el índice vectorial subyacente, manteniéndolo sincronizado ante inserciones, actualizaciones y borrados.
  \item \textbf{Funciones de consulta y distancia:}
  \begin{itemize}
    \item \texttt{VECTOR($x_1, \dots, x_D$)}: construye un vector literal de dimensión $D$.
    \item \texttt{AUDIO\_VECTOR(ruta | bytes)}: extrae MFCC y proyecta el vector BoAW ponderado con TF-IDF usando el \emph{codebook} del índice \texttt{AUDIO} de la tabla.
    \item \texttt{IMAGE\_VECTOR(ruta | bytes)}: extrae puntos clave SIFT y cuantiza su histograma BoVW con el \emph{codebook} del índice \texttt{IMAGE} de la tabla.
    \item \texttt{vector\_distance(col, consulta [, metrica])}: calcula la distancia entre el registro y el vector de consulta (menor valor indica mayor similitud).
  \end{itemize}
\end{itemize}

El motor extiende el lenguaje SQL con soporte declarativo para columnas e índices multimedia (\texttt{dbms/lib/sql/audio.go}, \texttt{image.go}, \texttt{vector.go}), además de funciones de extracción de características y operadores de ranking por similitud:

\begin{lstlisting}[style=sql,caption={Creación de índices vectoriales (IVF / HNSW) y multimedia (AUDIO / IMAGE) en SQL}]
-- 1. Indice HNSW e IVF sobre columnas VECTOR(D) explicitas
CREATE TABLE embeddings (id INT PRIMARY KEY, v VECTOR(128));
CREATE INDEX idx_emb_hnsw ON embeddings USING HNSW (v) WITH (M = 16, ef_search = 64, metric = 'cosine');
CREATE INDEX idx_emb_ivf  ON embeddings USING IVF  (v) WITH (nlist = 32, nprobe = 8, metric = 'euclidean');

SELECT id, vector_distance(v, VECTOR(0.12, 0.85, ...), 'cosine') AS distancia
FROM embeddings
ORDER BY vector_distance(v, VECTOR(0.12, 0.85, ...), 'cosine')
LIMIT 10;

-- 2. Búsqueda k-NN de audio por contenido (MFCC + BoAW)
CREATE TABLE canciones CLUSTERED BY (id) (
    id INT PRIMARY KEY, titulo VARCHAR(80), genero VARCHAR(40), archivo VARCHAR(120), v VECTOR(128)
);
CREATE INDEX idx_audio ON canciones USING AUDIO (archivo) WITH (k = 128);

SELECT id, titulo, genero, archivo,
       vector_distance(archivo, AUDIO_VECTOR('datos_demo/audio/muestras/000002.wav')) AS distancia
FROM canciones
ORDER BY vector_distance(archivo, AUDIO_VECTOR('datos_demo/audio/muestras/000002.wav'))
LIMIT 5;

-- 3. Búsqueda k-NN de imágenes por contenido (SIFT + BoVW)
CREATE TABLE imagenes CLUSTERED BY (id) (
    id INT PRIMARY KEY, nombre VARCHAR(60), categoria VARCHAR(30), archivo VARCHAR(120), v VECTOR(64)
);
CREATE INDEX idx_img ON imagenes USING IMAGE (archivo) WITH (k = 64);

SELECT id, nombre, categoria, archivo,
       vector_distance(archivo, IMAGE_VECTOR('datos_demo/imagenes/bosque_1.png')) AS distancia
FROM imagenes
ORDER BY vector_distance(archivo, IMAGE_VECTOR('datos_demo/imagenes/bosque_1.png'))
LIMIT 5;
\end{lstlisting}

Cuando el planificador (\texttt{planVectorKNN}) detecta el patrón \texttt{ORDER BY vector\_distance(col\_indexada, ...) LIMIT k} en orden ascendente, evita el recorrido secuencial y resuelve el top-$k$ directamente mediante el índice vectorial (\texttt{IVF}, \texttt{HNSW}, \texttt{AUDIO} o \texttt{IMAGE}). Desde la interfaz web (\texttt{VectorSearchPanel.jsx}) y el servidor HTTP (\texttt{dbms/cmd/server/}), el usuario puede consultar tanto por archivo subido como seleccionando una pista o imagen existente, reproduciendo o previsualizando los resultados mediante el \emph{endpoint} \texttt{/api/media/}.

\subsubsection{Metodología}

La evaluación experimental se ejecutó sobre el conjunto real \textbf{FMA Small} (\emph{Free Music Archive}), compuesto por \textbf{$7\,997$ pistas de audio} proyectadas a vectores \textbf{BoAW + TF-IDF de $D = 128$ dimensiones} (\texttt{resultados/audio.csv}). Se diseñaron dos experimentos utilizando el comando \texttt{audiobench}:

\begin{enumerate}
  \item \textbf{Escalabilidad ($N \in \{1\,000, 10\,000, 100\,000\}$, $k = 10$):} para $N = 1\,000$ se emplean las primeras $1\,000$ pistas reales. Para $N = 10\,000$ y $N = 100\,000$ se conservan intactas las $7\,997$ pistas reales y se completa hasta $N$ mediante \emph{bootstrap} determinista con perturbación gaussiana controlada ($\sigma = 0.03$) sobre las dimensiones activas y renormalización L2. En cada escala se promedian $100$ consultas ejecutadas siempre sobre pistas reales, comparando el escaneo secuencial contra \textbf{IVF-Flat} ($\text{nlist} = \lfloor\sqrt{N}\rceil$, $\text{nprobe} = \max(1, \lfloor\text{nlist}/4\rceil)$) y \textbf{HNSW} ($M = 16$, $\text{efConstruction} = 100$, $\text{efSearch} = 64$). Para $N = 100\,000$, el entrenamiento \emph{k-means++} de IVF utiliza una muestra de $32 \cdot \text{nlist} = 10\,112$ vectores antes de insertar los $100\,000$ registros.
  \item \textbf{Compromiso precisión vs.\ velocidad ($N = 7\,997$ pistas reales):} con $\text{nlist} = 89$, se evalúa el barrido $\text{nprobe} \in \{1, 2, 4, 8, 16, 22, 45, 89\}$ en IVF-Flat y $\text{efSearch} \in \{10, 16, 32, 64, 128, 256\}$ en HNSW bajo similitud del coseno y distancia euclidiana, midiendo latencia media, percentil 95 (P95), aceleración (\emph{speedup}) y \texttt{Recall@k} para $k \in \{5, 10, 20\}$.
\end{enumerate}

\subsubsection{Análisis de resultados}

\begin{itemize}
  \item \textbf{Punto de quiebre en escalabilidad ($N = 100\,000$).} Al crecer $100\times$ el catálogo de audio, la latencia del escaneo secuencial se degrada más de $139\times$ ($0.186\text{ ms} \rightarrow 25.915\text{ ms}$ en coseno) debido a que los $51.2\text{ MB}$ de vectores exceden la caché L3 y obligan a leer continuamente de memoria principal. En ese escenario, \textbf{IVF-Flat} mantiene un \texttt{Recall@10} del \textbf{100.0\%} respondiendo en $2.293\text{ ms}$ (\textbf{11.30$\times$} de aceleración), mientras que \textbf{HNSW} responde en apenas \textbf{0.118 ms} en coseno (\textbf{220.08$\times$}) y \textbf{0.085 ms} en euclidiana (\textbf{295.01$\times$}), manteniendo una latencia prácticamente submilisegundo en todo el rango evaluado.
  \item \textbf{Costo de construcción.} En distancia euclidiana con $N = 100\,000$, gracias al submuestreo de entrenamiento ($32 \cdot \text{nlist} = 10\,112$ vectores para \emph{k-means++}), \textbf{IVF-Flat se construye 2.65 veces más rápido que HNSW} ($7.66\text{ s}$ frente a $20.34\text{ s}$). En similitud del coseno, la construcción de IVF asciende a $32.62\text{ s}$ debido a la renormalización esférica de vectores y centroides exigida en cada iteración del entrenamiento.
  \item \textbf{Curva de compromiso en datos reales ($N = 7\,997$).} Como muestra la Figura~\ref{fig:audio-escalabilidad}(d), \textbf{IVF-Flat} exhibe una frontera de Pareto altamente sintonizable: con $\text{nprobe} = 8/89$ (inspeccionando solo el \textbf{9.0\%} de las celdas) alcanza \textbf{97.9\% de Recall@10 en 0.087 ms} (\textbf{18.82$\times$} de \emph{speedup} en coseno) y \textbf{98.1\% en 0.187 ms} en euclidiana. Con $\text{nprobe} = 16/89$ supera el \textbf{99.3\%} de precisión en ambas métricas.
  \item \textbf{Comportamiento de HNSW ante \texttt{efSearch}.} En la Tabla~\ref{tab:audio-tradeoff} se observa que el \emph{recall} de HNSW permanece constante ($44.0\%$ en coseno y $25.0\%$ en euclidiana) al variar $\text{efSearch}$ entre $10$ y $256$. Esto responde a un detalle de implementación del paquete subyacente (\texttt{coder/hnsw}), cuya primitiva \texttt{Search(q, k)} acota el tamaño de la lista dinámica de candidatos al valor solicitado $k$ ($k = 21$) en lugar de expandir el haz de búsqueda hasta \texttt{efSearch}. En consecuencia, HNSW ofrece la máxima velocidad de respuesta ($< 0.12\text{ ms}$ en $N = 100\,000$), mientras que IVF-Flat resulta preferible cuando la aplicación exige garantizar $\text{Recall@10} \ge 98\%$.
\end{itemize}

\begin{itemize}
  \item \textbf{Tiempo de construcción.} En los conjuntos pequeños, IVF-Flat presentó tiempos de construcción generalmente menores. Por ejemplo, con 997 imágenes y distancia euclidiana, IVF necesitó 19.64 ms, mientras que HNSW requirió 105.10 ms. Estos resultados muestran que el comportamiento de construcción depende del tamaño del conjunto y de la configuración utilizada.
  \item \textbf{Tiempo promedio de consulta.} Para conjuntos grandes, HNSW fue considerablemente más rápido durante las consultas. Con 99\,785 imágenes y distancia euclidiana, IVF necesitó 1.881 ms por consulta, mientras que HNSW utilizó solamente 0.082 ms, aproximadamente 23 veces menos tiempo. Esto muestra una ventaja importante de HNSW: su tiempo de consulta creció poco al aumentar el número de imágenes. 
  \item \textbf{Precisión de búsqueda (\texttt{Recall@10}).} El Recall@10 mide qué proporción de los diez vecinos más cercanos reales fue recuperada por el índice. En nuestros experimentos, IVF-Flat obtuvo los mejores resultados de precisión en todos los tamaños evaluados. Con aproximadamente 100\,000 imágenes, IVF alcanzó un Recall@10 de 95.15\% utilizando distancia euclidiana y 94.95\% con similitud del coseno. Por el contrario, HNSW presentó valores considerablemente menores. En el conjunto más grande, su Recall@10 fue de 3.23\% y 3.64\%, respectivamente. Esto significa que, aunque HNSW respondió más rápido, recuperó pocos de los diez vecinos esperados.
  \item \textbf{Consumo de memoria.} IVF-Flat presentó un consumo de memoria menor en todos los experimentos. Con aproximadamente 100\,000 imágenes, IVF utilizó entre 30.53 y 30.84 MB, mientras que HNSW necesitó alrededor de 164.9 MB. Esta diferencia se relaciona con las estructuras utilizadas por los algoritmos. HNSW mantiene conexiones entre vectores mediante un grafo, lo que requiere memoria adicional.
\end{itemize}

\section{Limitaciones y trabajo futuro}
% ===========================================================================

\begin{itemize}
  \item \textbf{Eliminación en el B+.} Hoy reconstruye el árbol en $O(N)$. Implementar redistribución y fusión de nodos bajará el costo de altas y bajas a $O(\log N)$.
  \item \textbf{Persistencia de índices en memoria.} Los índices clásicos y el R-Tree se reconstruyen al abrir la tabla; serializarlos en disco reduciría el tiempo de arranque.
  \item \textbf{Actualización incremental en SPIMI.} Actualmente una escritura invalida el índice invertido completo; incorporar segmentos delta fusionables en segundo plano evitaría reconstrucciones totales.
  \item \textbf{Granularidad de los bloqueos.} El aislamiento entre transacciones opera por tabla; bloqueos de intención (IS/IX) permitirían concurrencia a nivel de fila.
  \item \textbf{Tipos numéricos y JOIN.} Incorporar tipo flotante nativo (hoy las coordenadas \texttt{POINT} se almacenan como texto) y soporte para \texttt{RIGHT} y \texttt{FULL JOIN}.
  \item \textbf{Antimeridiano.} El cálculo de MINDIST con Haversine no contempla rectángulos que crucen $\pm180^\circ$.
  \item \textbf{Ampliación del haz \texttt{efSearch} en HNSW.} Sustituir o extender la rutina de búsqueda en la capa base de HNSW para desacoplar el tamaño del haz de exploración (\texttt{efSearch}) de $k$, permitiendo elevar el \emph{recall} por encima del $95\%$ en espacios dispersos TF-IDF sin reconstruir el grafo.
\end{itemize}

\section{Conclusiones}
% ===========================================================================

\begin{itemize}
  \item No existe una organización física ni un índice óptimo para todas las cargas de trabajo: el \emph{heap file} favorece la inserción (7.7$\times$ frente al secuencial), mientras que el archivo secuencial domina en búsqueda por clave primaria (760$\times$) y espacio en disco (4$\times$).
  \item Entre los índices clásicos, el hashing extensible lidera en igualdad (0.29~$\mu$s) y actualizaciones frecuentes (100$\times$), mientras que el B+ agrupado es superior en rangos y recorridos ordenados al aprovechar la contigüidad física.
  \item El R-Tree con división estilo R* y búsqueda \emph{best-first} resuelve consultas $k$-NN en tiempo casi independiente del tamaño del conjunto (0.023~ms con 100\,000 puntos), superando en 580$\times$ al escaneo secuencial y en 8$\times$ al GiST de PostgreSQL.
  \item La arquitectura SPIMI permite construir índices invertidos escalables mediante bloques acotados en RAM y fusión externa con \emph{Min-Heap}, habilitando consultas SQL ordenadas por relevancia con TF-IDF y BM25 mediante \texttt{MATCH}, \texttt{USING} y \texttt{SCORE()}.
  \item Con sesiones, 2PL estricto, WAL y detección de \emph{deadlocks}, el motor soporta transacciones concurrentes sin pérdida de actualizaciones ni lecturas sucias.
  \item En búsqueda multimedia sobre vectores BoAW/BoVW de 128 dimensiones, \textbf{IVF-Flat} y \textbf{HNSW} resuelven el cuello de botella del escaneo secuencial hasta $N = 100\,000$: IVF-Flat logra \textbf{95.0\%--100.0\% de Recall@10} con menor huella de memoria, mientras que HNSW alcanza latencias submilisegundo de \textbf{0.072--0.118 ms} (hasta \textbf{295$\times$} más rápido que el recorrido lineal).
\end{itemize}

\section{Reproducción de los experimentos}

El código fuente está disponible en \url{https://github.com/utec-database-2/dbms-go}. El archivo \texttt{README.md} del repositorio detalla la instalación y ejecución.

\begin{lstlisting}
git clone https://github.com/utec-database-2/dbms-go.git
cd dbms-go
go build ./...
\end{lstlisting}

Los experimentos de las Partes 1 y 2 se ejecutan con el comando principal del proyecto, escribiendo los resultados en \texttt{resultados/} (\texttt{archivos.csv}, \texttt{indices.csv} y \texttt{espacial.csv}) y generando las gráficas:

\begin{lstlisting}
dbms bench files    -n 1000,10000,100000 -queries 200
dbms bench indexes  -n 1000,10000,100000 -queries 500
dbms bench spatial  -n 1000,10000,100000 -queries 100 -pg-socket <socket>
dbms bench all      -n 1000,10000,100000
\end{lstlisting}

La demostración de concurrencia (Sección~\ref{sec:concurrencia}) se ejecuta con \texttt{dbms concurrencia [-hilos 5] [-depositos 3]}. Los experimentos de búsqueda textual (Parte 3) y multimedia de audio (Parte 4) se reproducen mediante:

\begin{lstlisting}
go run ./dbms/cmd/textbench
go run ./dbms/cmd/audiobench -sizes 1000,10000,100000 -queries 100 -metric all -csv resultados/audio.csv
dbms bench multimedia -sizes 1000,10000,100000 -queries 100
\end{lstlisting}
